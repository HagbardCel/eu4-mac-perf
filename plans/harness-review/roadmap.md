# Prioritized implementation roadmap

**Start with exact verdicts, a verifiable first case, and the existing compressed-input experiment.** An agent should be able to open the sealed terrain case, identify the last matching observation and first differing writer, and determine whether replaying the captured resources in GL can reproduce live GL. That result directly determines whether to spend the next hour on input capture or Metal semantics. [Assessment](assessment.md) · [small independent changes](quickwins.md)

**Priority rule.** P0 guards the truth of a current qualification or changes the experimental decision at the active blocker. P1 fixes a demonstrated input/state defect or recurring material loss of wall time. P2 improves transfer, attribution and maintainability once those contracts stabilize. Within a phase, prefer the smallest independent, reversible change whose result changes a real decision. Cost ranges below are engineering planning estimates for implementation and focused verification. Hardware scheduling, independent review and convergence of a research experiment are additional. Impact estimates are qualitative except for measured historical opportunities.

**Smallest useful release.** Ship 01's exact predicate and adapter projection, 05's startup pointer, and the native skip fix. Use them immediately on the stored control in 02, including the present 904 and candidate `34158764` before collecting more. Benchmark time to first correctly attributed difference. If a supported GL control still cannot reproduce live, publish the specific missing input/observable. A blocked but discriminating result is a valid deliverable. Do not require 03–08 to finish first. Run 03/04 as separate correctness candidates with their own controls. Schedule 06 before the next planned series of live acquisitions. Leave broad CI changes and physical artifact cleanup pending measured need.

## Verification policy for each implementation

Use the actual checked Python from the project. Run focused modules named in the step first, then affected neighbors. Example for 01:

```sh
python3.14 -m automation.python_runtime resolve
python3.14 -m automation.test_runner run --profile offline --module tests.test_m7_diagnosis --module tests.test_gfx_replay_checkpoints --module tests.test_agent_tools
python3.14 -m automation.test_runner run --profile offline --module tests.test_correction_accept --module tests.test_m7_pixel_diagnostics --module tests.test_m7_checkpoint_provenance
npm test --prefix dsh/eu4-tools-plugin
```

Use `npm test --prefix dsh/eu4-goal-plugin` for changed goal behavior. Inspect an existing invocation with `python3.14 -m automation.test_runner status --id <id>`. Run the full offline gate once at the end of an integrated candidate with `python3.14 -m automation.test_runner run --profile offline --label full`. For a failure, run the same modules against the pinned base via `run --cwd <base-worktree>` and `python3.14 -m automation.test_runner compare --base <base-id> --candidate <candidate-id>`. Retain checker, CI and independent PR review as separate decisions. A docs-only review needs relative-link and evidence checks.

**Milestones.** A succeeds when independent clients agree on all negative verdicts and reach the same verified case on startup. B succeeds per supported operation when exact prerequisites, producer, scope and controls agree; an unsupported state is surfaced at its first affected observation. C succeeds when normal completion, interruption and rejection all leave durable outcomes and restore owned resources. D succeeds when a fresh agent independently reproduces those results and the team can compare progress per wall hour and resource use across equivalent runs. Keep the performance-optimized backend at design stage until a faithful workload meets the exact criteria and profiling identifies an actual bottleneck.
