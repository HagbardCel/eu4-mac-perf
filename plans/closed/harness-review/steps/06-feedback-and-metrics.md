# 06 · Measure verified progress and shorten feedback loops

**Objective.** Choose the next test or replay from the cost of reaching a trustworthy result. A successful tool return, completed DSH turn or low final pixel count alone cannot measure migration progress.

1. In automation/dsh_efficiency.py analyze/execution_summary derive goal phase from the final goal/change record, keeping turn/end, action attempted and checker outcome in separate fields. Preserve the old export window and add goal-active wall time. Optionally join an explicitly supplied campaign guard ledger, capture/replay receipts and test-run IDs after matching objective/run, capture identity and time interval. T1236 counts as a verification. Count reserves, claims, confirmed starts, completed executions and outcomes separately. Unavailable evidence is unknown, not zero. Parallel jobs have a union wait and separate job span; do not add them.
2. Add a compact sanitized fixture derived from sequences 7, 471–491, 713, 791, 1236, 1254 and 1263. Include a launch denied before spawn, interrupted claim, overlapping job and stale/foreign ledger. Assert blocked goal with completed turn, two confirmed replays, one verified case and a single confirmed launch for the representative case. Metrics must not expose raw shaders or unrestricted logs. Preserve historical analyses and label schema changes.
3. Use test_runner for focused → neighboring → final offline discovery. Add optional timing to the discovery result by module/test ID including skips and setup/teardown overhead where observable. Use wall time for whole suite and report unallocated overhead. Record revision, host architecture, Python, cache warmth, selection, pass/fail and skipped IDs. The Linux workflow serializes manifest and discovery; test_profiles._execute_required_tests dynamically executes required IDs. An inventory check alone is insufficient. If timings justify deduplication, produce a discovery execution receipt in the same run and validate required IDs actually executed exactly as required, plus floor, selection and skip rules. Preserve the standalone manifest command. Fail on truncated receipts, mismatched head, subprocess timeout or discovery crash. Keep all tests until equivalence demonstrated.
4. Establish three repeatable pilots. (a) Offline retrieval from the pinned 616 seal: no launches, verify and report writer/interval, depth function, unsupported states and one discriminating experiment. (b) Seeded one-pixel/overdraw fault and exact-control regression: checker must accept only the valid correction and reject the wrong intermediate. (c) Operational smoke under the Web profile with interrupted/restarted reservation: zero duplicate starts and truthful terminal conclusion. Run on a frozen checkout/objective/model/tool configuration and same machine, recording warm/cold cache separately. Use multiple paired trials (start with three), median and range; identify budget stops and human interventions. For a real migration campaign report distinct accepted source corrections and exact cases preserved per active hour, plus bounded intervals narrowed with case evidence as a separate intermediate endpoint. A blocked goal earns no accepted correction.
5. Dashboard unnecessary. Store small JSON beside existing pilot summaries: goal wall time, time to first verified case/first discriminating result, native/shell/model calls and returned characters, actual GPU executions/game launches, time per build/test, bytes pinned and checker/regression outcomes. A/B the entry/handoff changes on the same fixed task; if the arm loses a required checkpoint or regression it cannot win on speed. Use the latest trace's 44m39s/201 tools as descriptive context; offline-only trials have a different denominator.
