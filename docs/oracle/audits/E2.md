## Candidate binding (acceptance contract)

E2 prepares known-good candidate **inputs** (`acceptance_candidate.py`: frozen P4
fields including four-file `source_sha256` and a real RE1 executable copy). That
fixture does not establish EU IV runtime provenance and is not authoritative
trusted-build metadata.

E1 must independently verify submitted source and executable identities and enforce
the frozen production build record (E1-owned JSON per remediation rev 4). Caller-
supplied digests and acceptance-generated records do not prove provenance.

Integration tests require a **binding-specific** failure in `promotion.reasons` or
`evaluation.failures` when the submitted executable digest disagrees with the artifact
on disk, with eligible reference admission.

## Negative controls

- `false_certifier_stand_in`: schema-valid `certified` with a recorded mismatch.
- `forged_executable_binding_stand_in`: inconsistent executable binding (helper-level).
- `unrelated_failure_stand_in`: eligible admission, failed promotion without binding
  diagnostics (must not satisfy the binding-failure helper).

Each control is rejected inside the test module; CI stays green.

## Adversarial fixtures (E2-owned)

- Resealed `metadata.json` `{}` → session ineligible; sealed bytes unchanged.
- Certificate publish with `tier1-certificate.json` symlink into the seal → seal
  immutable (requires E1 mkstemp publish fix).
- Forged `build_identity` under production record → `assert_build_identity_binding_failure`.
